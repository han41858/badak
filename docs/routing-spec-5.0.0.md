# badak 5.0.0 라우팅 명세

- 상태 : 확정된 설계 기준, `next` 브랜치에서 구현
- 작성일 : 2026-10-22
- 대상 버전 : 5.0.0 (호환성을 깨는 변경)

## 1. 목표와 원칙

같은 METHOD의 요청 하나에 매칭되는 라우팅 규칙은 **항상 하나**여야 한다. 둘 이상이 매칭될 수 있으면 등록 시점에 오류를 낸다(Fast Fail).

- 충돌을 우선순위로 해결하지 않는다. 일반 경로도 `:`, `?`, `+`, `*`보다 우선하지 않는다.
- 일반 경로, `:`, `?`, `+`, `*`의 모든 조합을 실제 매칭 집합으로 검사한다.
- `**`는 "다른 라우트가 전체 경로에 매칭되지 않을 때만 쓰는 폴백"으로 유지한다. 단, 같은 깊이의 `**` 폴백도 매칭되는 규칙은 METHOD마다 하나여야 한다(5절).
- 이 보장이 있으면 매칭 결과는 등록 순서와 탐색 순서에 영향을 받지 않는다.
- 등록 검사와 요청 매칭은 **같은 패턴 해석, 같은 토큰 모델**을 쓴다.
- 새 공개 API는 추가하지 않는다. `*`의 의미 변경과 기호 조합 허용은 2절에 정의한다.

## 2. 경로 조각 문법

### 2.1 기호의 의미

| 패턴 | 의미 | 매칭 | 비매칭 |
|---|---|---|---|
| `users` | 리터럴 (퍼센트 인코딩은 디코딩해서 비교) | `users` | `user` |
| `:id` | 조각 하나, 아무 문자 1개 이상 | `7`, `me` | (빈 조각 없음) |
| `*` (조각 전체) | 조각 하나, 아무 문자 1개 이상 | `a.png` | — |
| `ab?cd` | 바로 앞 문자 `b`가 0~1회 | `acd`, `abcd` | `abbcd` |
| `ab+cd` | 바로 앞 문자 `b`가 1회 이상 | `abcd`, `abbcd` | `acd` |
| `ab*cd` | `ab`와 `cd` 사이에 아무 문자 0개 이상 | `abcd`, `abbcd`, `abXYZcd` | `acd`, `aXcd`, `abc` |
| `ab*` | `ab` 다음에 아무 문자 0개 이상 | `ab`, `abc` | `a` |
| `*.png` | 아무 문자 0개 이상 다음에 `.png` | `a.png`, `.png` | `a.jpg` |
| `**` (조각 전체) | 나머지 경로 전체, 폴백 (5절) | — | — |

- `?`, `+`는 바로 앞 **문자 하나**에 작용하는 수량자다.
- `*`는 앞 문자와 상관없는 **와일드카드**다. 조각 전체 `*`도 같은 규칙이며, 경로 조각은 비어 있을 수 없으므로 결과적으로 1개 이상이 된다.
- 문법 기호는 **원본 문자열에서 인코딩되지 않은** `:`(조각 맨 앞), `?`, `+`, `*`뿐이다. 퍼센트 인코딩된 문자는 디코딩 결과와 상관없이 리터럴이다(2.3절).
- 문자 비교는 디코딩된 Unicode code point 기준이다.

### 2.2 조합 규칙

| 조각 | 결과 | 이유 |
|---|---|---|
| `ab?c+d` | 허용 | `?`, `+`가 각각 앞 문자에 작용 |
| `a*b*c` | 허용 | 와일드카드 여러 개, 문법 `*`가 연속되지 않음 |
| `ab?c*` | 허용 | |
| `*abc` | 허용 | 와일드카드는 앞 문자가 필요 없음 |
| `?abc`, `+abc` | 오류 | 수량자가 작용할 앞 문자가 없음 |
| `ab??`, `ab++`, `ab?+`, `ab+?` | 오류 | 수량자가 연속됨 |
| `ab?*`, `ab+*`, `ab*?`, `ab*+` | 오류 | 수량자와 와일드카드가 연속돼 읽기 어려움 |
| `**` (조각 전체) | 폴백 | 5절 |
| `a**`, `**b`, `a**b`, `***`, `a***b` | 오류 | 문법 `*`가 연속됨. `**`는 조각 전체에서만 폴백 문법이다 |
| `a*%2A`, `%2A*b` | 허용 | `%2A`는 리터럴 `*`이므로 문법 `*`가 연속된 것이 아님 |
| `%2A%2A` | 일반 경로 | 리터럴 문자열 `**`, 폴백이 아님 |
| `ab:id` | 오류 | `:`는 조각 맨 앞에서만 문법 (4.0.0 규칙) |
| `:id?` | `:` 조각 | `:` 뒤 전체가 파라미터 이름 (4.0.0 규칙) |
| `**`가 마지막 조각이 아님 | 오류 | 4.0.0 규칙 |

- 연속 여부는 디코딩한 문자열이 아니라 원본 기준으로 판단한다. 기준은 **문법 기호 두 개가 연달아 있는지**다.

### 2.3 파싱과 정규화

1. **파싱** : 원본 라우팅 패턴을 왼쪽부터 읽으며 각 문자를 분류한다.
   - **문법 문자** : 인코딩되지 않은 `?`, `+`, `*`, 조각 맨 앞의 `:`
   - **리터럴 문자** : 그 밖의 모든 문자, 그리고 `%XX` 열을 UTF-8로 디코딩한 각 문자
   - 결과는 `{ syntax }` 또는 `{ literal }` 항목의 열이다(4.x `splitRouteKey()`와 같은 구조).
2. **분류 보존** : 디코딩한 뒤에도 각 문자의 문법/리터럴 분류를 유지한다. 토큰화, 교집합 판정, 매칭, 오류 메시지는 모두 이 항목 열에서 만든다. 분류를 버리고 디코딩된 문자열을 다시 파싱하지 않는다.
3. **정규화(canonical key)** : 항목 열을 다시 문자열로 직렬화한 것이다.
   - 문법 문자는 그대로 둔다.
   - 리터럴 문자 가운데 문법 기호와 같은 모양이거나 경로에 그대로 쓸 수 없는 문자는 **항상 퍼센트 인코딩**한다. 대상은 `%`, `/`, `:`, `?`, `+`, `*`, 공백, 제어 문자다.
   - 그 밖의 리터럴 문자는 디코딩된 형태로 둔다. 예 : `%ED%95%9C` → `한`.
   - 인코딩은 대문자 16진수로 통일한다. 예 : `%2a` → `%2A`.
   - 그래서 정규화는 문법/리터럴 구분을 지우지 않는다. 예를 들어 `ab%2Acd`(리터럴 `*`)와 `ab*cd`(와일드카드)는 **서로 다른 키**이며, 재등록(교체)으로 처리하지 않는다.
   - 다만 두 패턴의 매칭 집합은 겹친다(리터럴 문자열 `ab*cd`가 양쪽에 모두 매칭). 따라서 METHOD가 같으면 4절에 따라 **등록 순서와 상관없이 충돌 오류**다.
4. **불변 조건**
   - 정규화한 키를 다시 파싱하면 원래와 같은 항목 열이 나온다(왕복 보존).
   - 표기가 달라도 항목 열이 같으면 정규화한 키가 같다. 예 : `/한글` ≡ `/%ED%95%9C%EA%B8%80`, `col%6Fu?r` ≡ `colou?r`.
5. **오류** : 잘못된 퍼센트 인코딩(`%ZZ`, 불완전한 UTF-8 열)은 등록 오류다(4.0.0 규칙).

## 3. 토큰 모델과 교집합 판정

모든 경로 조각(`**` 제외)을 하나의 토큰 열로 바꾼다.

| 토큰 | 소비 |
|---|---|
| 리터럴 문자 `c` | `c` 1회 |
| 선택 문자 `c?` | `c` 0~1회 |
| 반복 문자 `c+` | `c` 1회 이상 |
| 와일드카드 | 아무 문자 0회 이상 |

변환 규칙은 다음과 같다.

| 조각 | 토큰 열 |
|---|---|
| 일반 경로 | 리터럴 문자의 열 |
| `:id`, `*` | 와일드카드 하나 (빈 문자열 제외 규칙에 따라 1개 이상) |
| `ab*cd` | `a`, `b`, 와일드카드, `c`, `d` |

- **매칭** : `matchPatternTokens(tokens, frag)`는 NFA 시뮬레이션이며 백트래킹이 없다.
- **교집합** : `patternTokensIntersect(a, b)`는 두 토큰 열의 곱 오토마톤을 탐색해 **비어 있지 않은** 공통 문자열이 있는지 판정한다. 와일드카드는 상대의 어떤 문자와도 짝지어진다.
- 4.x `fragment-pattern.ts`를 확장한다. 정규식을 쓰지 않고, 문자열을 전개하지 않는다.

| 작업 | 비용 |
|---|---|
| 조각 매칭 | O(m × L) — m : 패턴 토큰 수, L : 조각 길이 |
| 조각 교집합 | O(m × n) — m, n : 두 패턴의 토큰 수 |
| 라우트 하나 등록 | O(R × D × m × n) — R : 같은 METHOD·같은 조각 수인 기존 라우트 수, D : 조각 수. 라우팅 트리로 R을 줄일 수 있다 |

## 4. 전체 경로 충돌 규칙

두 라우트는 다음 세 조건을 모두 만족하면 충돌한다.

- METHOD가 같다.
- 조각 수가 같다.
- **모든 위치의 조각이 교집합을 가진다.**

`**`가 없는 라우트는 조각 수가 고정이므로, 조각 수가 다르면 겹치지 않는다.

- METHOD가 다르면 같은 패턴도 등록할 수 있다. HEAD는 따로 등록하는 API가 없으므로 GET으로만 검사한다.
- 정규화한 키와 METHOD가 같으면 충돌이 아니라 재등록이며, 기존 핸들러를 교체한다(4.0.0과 같음).
- 매칭 집합이 같아도 키가 다르면 충돌이다. 예 : `:id`와 `:name`, `*`와 `:id`.
- 끝의 `/`는 무시한다. `/img`와 `/img/`는 같은 경로다.

| 라우트 A | 라우트 B | 결과 | 공통 경로 / 이유 |
|---|---|---|---|
| `GET /users/me` | `GET /users/:id` | 오류 | `/users/me` |
| `GET /files/readme` | `GET /files/*` | 오류 | `/files/readme` |
| `GET /abc` | `GET /ab+c` | 오류 | `/abc` |
| `GET /abc` | `GET /ab?c` | 오류 | `/abc` |
| `GET /abc` | `GET /ab*` | 오류 | `/abc` |
| `GET /ab*cd` | `GET /abXcd` | 오류 | `/abXcd` |
| `GET /ab*cd` | `GET /acd` | 허용 | `ab*cd`는 `acd`에 매칭되지 않음 |
| `GET /ab*cd` | `GET /ab%2Acd` | 오류 | `/ab%2Acd`(디코딩하면 `ab*cd`)에 두 규칙이 모두 매칭 |
| `GET /ab%2Acd` | `GET /ab%2Acd` | 교체 | 같은 키, 재등록 |
| `GET /a*` | `GET /*b` | 오류 | `/ab` |
| `GET /a*` | `GET /b*` | 허용 | 첫 문자가 다름 |
| `GET /*.png` | `GET /*.jpg` | 허용 | 끝이 다름 |
| `GET /a/:id` | `GET /a/b+` | 오류 | `/a/b` |
| `GET /a/:id/details` | `GET /a/b+/details` | 오류 | `/a/b/details` |
| `GET /a/:id/details` | `GET /a/b+/settings` | 허용 | 세 번째 조각이 겹치지 않음 |
| `GET /users/:id/a` | `GET /users/:name/b` | 허용 | 같은 이유 |
| `GET /a/:id` | `POST /a/b+` | 허용 | METHOD가 다름 |
| `GET /a/:id` | `GET /a/:id/b` | 허용 | 조각 수가 다름 |
| `GET /img/*` | `GET /img/:id` | 오류 | 매칭 집합이 같음 |
| `GET /users/:id` | `GET /users/:name` | 오류 | 같음 |
| `GET /한글/:id` | `GET /%ED%95%9C%EA%B8%80/:name` | 오류 | 정규화 후 같음 |
| `GET /users/:id` | `GET /users/:id` | 교체 | 재등록 |
| `GET /한글` | `GET /%ED%95%9C%EA%B8%80` | 교체 | 정규화 후 같은 키 |

## 5. `**` 폴백 규칙

`**`는 다른 라우트와의 충돌 검사에서 제외한다. 단, **METHOD와 깊이가 같은 `**`끼리 앞부분이 겹치면 오류**다.

- **정의** : `P/**`에서 `P`(조각 k개)를 앞부분, k를 깊이라고 한다.
- **후보** : 요청 경로의 앞 k개 조각이 `P`에 매칭되는 `**` 라우트. 남은 조각은 0개 이상이다(`/files/**`는 `/files`에도 매칭).
- **폴백 조건** : `**`가 없는 라우트가 **어느 METHOD로도** 전체 경로에 매칭되지 않을 때만 폴백한다.
- **선택**
  1. 깊이가 가장 큰 후보를 **모두** 모은다. METHOD가 다르면 앞부분이 겹치는 후보가 여럿일 수 있다.
  2. 그중 요청 METHOD(HEAD는 GET)의 핸들러를 쓴다. 등록 검사가 있으므로 METHOD마다 많아야 하나다.
  3. 해당 METHOD가 없으면 405이고, `Allow`는 그 깊이 후보들의 METHOD 합집합이다(GET이 있으면 HEAD 포함).
  4. 더 얕은 폴백으로 내려가지 않는다(4.0.0과 같음).
- **등록 검사** : METHOD와 k가 같은 두 `**` 라우트의 앞부분이 모든 위치에서 교집합을 가지면 오류다. 앞부분이 정규화 후 같으면 교체한다.
- k가 다른 `**`는 함께 등록할 수 있다. 더 깊은 쪽이 우선하는 것은 명시된 규칙이며, 충돌을 우선순위로 해결하는 것과는 다르다.

| 라우트 A | 라우트 B | 결과 |
|---|---|---|
| `GET /**` | `GET /files/**` | 허용, `GET /files/x` → B |
| `GET /files/*` | `GET /files/**` | 허용, `/files/a` → A, `/files/a/b` → B |
| `GET /files/**` | `GET /files/:id` | 허용, `/files/1` → B, `/files/1/2` → A |
| `GET /a/:id/**` | `GET /a/b+/**` | 오류 (깊이 2, `/a/b`) |
| `GET /:x/**` | `GET /a/**` | 오류 (깊이 1, `a`) |
| `GET /a/:id/**` | `POST /a/b+/**` | 허용. `GET /a/bb/c` → A, `POST /a/bb/c` → B, `PUT /a/bb/c` → `405 Allow: GET, HEAD, POST` |
| `GET /a/:id/x/**` | `GET /a/b+/**` | 허용, `/a/bb/x/y` → A (깊이 3), `/a/bb/z` → B |

## 6. 매칭 알고리즘

조각마다 우선순위가 가장 높은 하나만 고르던 4.x 방식을 **매칭되는 모든 후보를 탐색하는 방식**으로 바꾼다.

4.x에서 이 차이가 드러나는 예 :

- `GET /a/:id/details` + `GET /a/b+/settings` : `/a/bb/settings`가 404다.
- `GET /a/:id` + `POST /a/b+` : `POST /a/bb`가 405다.

알고리즘 :

1. 요청 경로를 토큰화한다(4.0.0 규칙). 잘못된 퍼센트 인코딩은 400이다.
2. 라우팅 트리를 깊이 우선으로 탐색하며, 현재 조각에 매칭되는 자식을 **모두** 따라간다. 지나친 `**` 자식은 깊이와 함께 폴백 후보로 기록한다.
3. 전체 경로에 매칭되고 라우팅 함수가 있는 노드를 모은다. METHOD마다 많아야 하나다.
4. 모은 노드가 하나 이상이면 요청 METHOD(HEAD는 GET)의 함수를 쓴다.
   - 해당 METHOD가 없으면 405이고, `Allow`는 모은 노드들의 METHOD 합집합이다(GET이 있으면 HEAD 포함). 이때 폴백하지 않는다(4.0.0과 같음).
   - 예 : `GET /a/:id` + `POST /a/b+`에서 `PUT /a/bb` → `Allow: GET, HEAD, POST`.
5. 모은 노드가 없으면 5절의 폴백 규칙을 적용한다. 후보가 없으면 404다.
6. `ctx.params`는 선택된 라우트의 경로에서만 만든다. 탐색하다 버린 경로의 값은 섞이지 않는다.

탐색 비용 요구사항 :

- 특정 복잡도를 보장하기보다 다음 조건을 지킨다.
  - 같은 (트리 노드, 조각 위치) 상태를 중복 탐색하지 않는다.
  - 일반적인 라우트 구성에서 불필요한 전체 탐색을 하지 않는다. 예 : 리터럴 자식은 인덱스로 찾는다.
  - 악의적인 요청 경로(아주 긴 조각, 많은 조각)로 CPU 사용이 과도하게 늘지 않는다.
- 성능 검증은 다음 둘로 나눈다.
  - **회귀 검사(CI)** : 명백한 회귀(지수적 증가 등)만 넉넉한 기준으로 확인한다.
  - **벤치마크(별도 스크립트)** : 깊이 10, 다중 분기, 라우트 1,000개를 측정한다. CI 환경은 편차가 크므로 밀리초 기준은 CI에 두지 않는다.

## 7. 등록 방식과 원자성

다음 등록 방식 모두에 같은 검사를 적용한다.

- `app.route()` 한 번 또는 여러 번 호출
- `get()`, `post()`, `put()`, `patch()`, `delete()`
- 위 두 방식의 혼합
- `route()` 객체 하나 안에서 서로 다른 키가 같은 노드를 만드는 경우(4.0.0 병합 규칙)
- 등록 순서를 바꾼 경우

등록 호출 하나는 "전체 검사 → 성공한 경우에만 트리 반영"으로 처리한다. 충돌이 나면 기존 라우팅 트리와 핸들러는 바뀌지 않는다.

정적 파일(`static()`, `setSPARoot()`) :

- 파일 라우트(GET)는 `listen()` 때 같은 검사를 받는다. 예 : `static('/', dir)`에 `style.css`가 있으면 `GET /:slug`와 충돌한다.
- `listen()` 한 번의 정적 라우트 전체(모든 정적 폴더의 파일 라우트와 SPA의 `**` 라우트)를 **라우트 객체 하나로 모아 한 번에 검사하고 한 번에 반영**한다.
- 충돌이 나면 `listen()`이 거부(reject)되고 서버는 시작하지 않는다. 라우팅 트리, 정적 파일 캐시(`_staticCache`), SPA 루트는 `listen()` 호출 전 상태 그대로다. 일부만 등록되지 않는다.
- 충돌을 고친 뒤 다시 `listen()`하면 처음 호출한 것과 같은 결과가 나온다.
- `listen()`은 정적 라우트 등록을 반드시 기다린다. 4.x는 `this.get(...)`을 기다리지 않아서 오류가 처리되지 않은 Promise 거부가 된다.
- 정적 폴더 두 개가 같은 파일 경로를 가지면 재등록(교체)으로 처리한다(4.0.0과 같음).
- `stop()` 후 다시 `listen()`할 때 정적 라우트를 중복 등록하지 않는다. 같은 키는 교체하고, 캐시는 다시 만든다.

## 8. 오류 처리

충돌 오류에는 METHOD와 두 라우트 패턴을 포함한다.

```text
Conflicting routes for GET:
  /a/:id/details
  /a/b+/details
```

```text
Conflicting fallback routes for GET at depth 2:
  /a/:id/**
  /a/b+/**
```

- 4.x의 `duplicated colon/question/plus/asterisk routing` 메시지는 위 형식으로 통일한다.
- 패턴 문법 오류(2.2절)는 `invalid route` 계열 메시지로 내고, 문제가 된 조각과 이유를 포함한다. 예 : `invalid route : 'ab?*' : a quantifier and a wildcard can't be adjacent`.
- 정적 파일 충돌 오류에는 정적 폴더 경로와 파일 경로를 함께 표시한다.
- 바뀐 메시지는 CHANGELOG에 기록한다.

## 9. 호환성과 마이그레이션

| 경우 | 4.x | 5.0.0 | 마이그레이션 |
|---|---|---|---|
| `/users/me` + `/users/:id` | 허용, `me` 우선 | 오류 | `/me`로 분리하거나 `:id` 핸들러에서 `me`를 분기 |
| `/files/readme` + `/files/*` | 허용 | 오류 | 위와 같음 |
| `static('/', dir)` + `/:slug` | 허용, 파일 우선 | 파일 이름이 겹치면 `listen()` 실패 | 정적 파일을 하위 경로로 옮기거나 `setSPARoot()` 사용 |
| `/img/*` + `/img/:id` | 허용, `:` 우선 | 오류 | 하나만 사용 |
| `/a/:id` + `/a/b+` (`?`, `*`도 같음) | 허용, `b+`는 쓰이지 않음 | 오류 | 쓰이지 않던 라우트 제거 |
| `ab*cd` | `acd`, `aXcd`에도 매칭 | `abcd`, `abXYZcd` 등 | `*` 앞 문자까지 와일드카드였던 동작을 썼다면 패턴 수정 |
| `user1*` (4.x README 예시) | `user`에도 매칭 | `user1`로 시작하는 조각만 | `user*`로 수정 |
| `*abc`, `a*b*c`, `ab?c+`, `ab?c*` | 등록 오류 | 허용 | 없음 |
| `a**b` 등 조각 안의 연속된 `*` | 해석이 불명확 | 등록 오류 | 패턴 수정 |
| `/a/:id/x` + `/a/b+/y` | 허용, `/a/bb/y`는 404 | 허용, `/a/bb/y` → `b+` 라우트 | 동작이 바뀜, 확인 필요 |
| `GET /a/:id` + `POST /a/b+` | `POST /a/bb`는 405 | `POST /a/b+` 라우트 | 동작이 바뀜, 확인 필요 |
| `/users/:id/a` + `/users/:name/b` | 오류 | 허용 | 없음 |
| `/files/*` + `/files/**` | 오류 | 허용 | 없음 |
| `/ab*` + `/xy*` | 오류 | 허용 | 없음 |
| `/abc` + `/ab+c`, `/abc` + `/ab?c` | 오류 | 오류 | 메시지만 바뀜 |
| 오류 메시지 | `duplicated … routing` | `Conflicting routes for …` | 메시지를 검사하는 테스트 수정 |

- 위 표와 마이그레이션 방법을 CHANGELOG에 기록한다.
- README(영문·한국어)의 특수 라우팅 절과 Routing priority 절을 "매칭되는 규칙은 하나" 원칙과 2절 문법으로 다시 쓴다.
- 다음은 바꾸지 않는다 : HEAD의 GET 처리, 요청 본문 파싱, 미들웨어, 인증, 정적 파일 응답(ETag, Cache-Control).

## 10. 테스트 요구사항

- **문법** : 2.1절 표의 매칭·비매칭 사례 전부, 2.2절의 허용·오류 조합 전부.
- **파싱·정규화**
  - 인코딩된 리터럴과 문법 기호가 섞인 패턴(`a%3Fb?`, `%2B+`, `a*%2A`, `%3Aid`)의 항목 열 확인
  - 정규화 왕복 보존(무작위 패턴)
  - 표기가 달라도 같은 패턴이면 같은 키가 되는지
  - `ab%2Acd`와 `ab*cd`가 다른 키이면서, 두 등록 순서 모두에서 충돌 오류가 나는지
  - `*` 연속 : `a**`, `**b`, `a**b`, `***`는 오류, `a*%2A`는 허용, `%2A%2A`는 일반 경로
- **조각 교집합** : 리터럴·`:`·`*`(조각 전체·부분)·`?`·`+`의 모든 쌍에 대한 충돌·비충돌 사례. 무작위 패턴(문자 `a`·`b`, 기호 혼합)의 결과를 brute force와 비교한다(짧은 문자열 전수 나열 + 정규식 오라클). `matchPatternTokens`도 같은 오라클로 비교한다.
- **전체 경로** : 깊이가 다른 경우, 뒤쪽 조각만 다른 경우, 같은·다른 METHOD, 정규화, 재등록과 교체.
- **`**`** : 같은·다른 깊이, METHOD가 다른 같은 깊이 후보, 가장 깊은 폴백 선택, 폴백에서의 405 `Allow` 합집합, 얕은 폴백으로 내려가지 않는지.
- **등록 방식** : `route()` 객체 하나 안에서의 충돌, 서로 다른 시점의 등록, 모든 등록 순서(순열), 충돌 후 원자성.
- **정적 파일** : 충돌 시 `listen()` 거부, 부분 등록 없음(트리·캐시·SPA 루트), 수정 후 재시도, `stop()` 후 `listen()`, 처리되지 않은 Promise 거부 없음.
- **매칭** : 무작위 라우트 집합과 요청 경로를 만든다. 등록에 성공하면 실제 매칭 결과가 brute force(모든 라우트를 직접 대 보고 정확히 하나인지 확인)와 일치하는지, 등록이 실패하면 실제로 두 규칙이 함께 매칭되는 경로가 있는지 확인한다.
- **HTTP** : 405 `Allow` 합집합, HEAD, `ctx.params`에 탐색하다 버린 경로의 값이 섞이지 않는지.
- **성능** : CI에는 명백한 회귀 검사만 둔다. 깊이 10, 다중 분기, 라우트 1,000개는 별도 벤치마크로 측정한다.
- **회귀** : 기존 테스트 전체. 5.0.0에서 의도적으로 바뀐 테스트는 PR에 목록으로 적는다.

## 11. 완료 조건

- 같은 METHOD의 요청 URL 하나에 대해 `**`를 제외한 서로 다른 라우트가 동시에 매칭되지 않음을, 그리고 같은 깊이의 `**` 폴백도 METHOD마다 하나만 매칭됨을 등록 시점에 보장한다.
- 등록 검사와 요청 매칭이 같은 파싱 결과(2.3절)와 같은 토큰 모델(3절)을 쓴다.
- lint, test, test:types, ESM/CJS build, test:types:dist가 모두 통과한다.
- 구현은 `dev`를 향하는 PR로 작성하고 자동 머지하지 않는다.
